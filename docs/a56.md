# The Galaxy A56 (SM-A566E) port

> **Status (2026-11-23, OneiOS issue 73).** A Galaxy A56 owner can make our own iOS 16.5 image and start it with our
> app and runtime: the OneOS fork offers the iOS kind on an SM-A566 and Makes the image with `profiles/ios-16.5-a56.toml`
> ("In the OneOS fork" below). **None of it has run on an A56**: there is none here, so every A56 line below is built
> and host-tested, not booted. The S24 Ultra / iOS 27 defaults are unchanged: every A56 behaviour is behind the host
> table's `galaxy-a56` row, the image's build (`20F66`) or the fork's phone profile.
> Since 2026-11-21 xnuhost recognises the A56 at its start (`galaxy-a56` in `runtime/bridges/hw/host_device.rs`,
> `docs/hardware.md` 7h: `SM-A566*`, `a56x`, `ro.soc.model` `s5e8855`) and defaults to `--gpu 2d` there (no KGSL).

## Issue 73: why the other fork's image stops at its first start

The user's log (MRDinar, 2026-11-23): `ChunkCompression.cpp:415: /usr/lib/dyld: invalid resource map`, then `OneiOS
Data: newfs_apfs did not run: 13`, then `panic: offline scratch Data mount failed: 13`. The image was
`Musicalista/OneiOS-A56` v1.0.0's (`ios16.5-a56-image.tar.gz.part00/01`, read here on 2026-11-23). It is not Apple's
images: its `os.img` (2,476,699,648 bytes, one unsealed volume `System`) and `systemos.img` (12,505,088 bytes) were
written by that fork's own APFS writer (its release notes: "legacy mkapfs.py tools"); its trust caches are 24A446's
(sizes 92,017, 3,191 and 863), and its Data seed and overlay were made from a 24A446 root (its `report.txt`: `build
24A446`). Only its `app.img` is Apple's 20F66 AppOS.

**The cause.** iOS reads a compressed (decmpfs) file of kind 4 through its resource fork, a whole Mac resource fork
with a resource map. In 8,340 of the 40,179 compressed files of that `os.img` (and 272 of 1,397 in its `systemos.img`)
the map's first 16 bytes hold a copy of the fork's header; Apple's writer leaves them zero, and every compressed file
of Apple's 24A446 and 20F66 images has Apple's map (`oneios-tool image apfs-check`, tools/oneios-tool/README.md). `dyld`
is one of them, so the guest's first exec (`/sbin/newfs_apfs`, to make the Data volume) fails, and the kernel's Data
step panics. That the 16 bytes are what iOS refuses is inferred (the message names the map; it is the only difference
found), not read in Apple's code. Our decoder decoded those files (it reads only the data's place), so nothing here
caught it before: `image verify` of a set folder now reads every compressed file as iOS needs it, and the other
fork's set fails it.

## Our A56 image: iOS 16.5 (20F66), all of it Apple's

The owner's call (2026-11-23): iOS 16.5 itself, not a mix. `profiles/ios-16.5-a56.toml` pins Apple's iPhone X
restore file (iPhone10,3 / iPhone10,6, d22ap): the OS, SystemOS and AppOS images, their trust caches and root hashes,
and the Data seed made from that OS image's `/private/var`. The one part that is not 16.5's is `kernel.kc`: OneiOS's
hosted XNU prelinked with the iPhone18,2 24A446 kexts, the only collection there is (a 16.5 kext pairing does not
exist; the other fork ran 16.5 on the same 24A446 collection). The old reference profile's URL (Apple answers 403) and
SHA-256 were wrong; the new pins are read from Apple's file (the profile's header). The OS image is a UDIF disk image,
which the image build converts (`image udif-raw`, docs/image-format.md section 1). Built on the Linux PC
(docs/building.md "The iOS 16.5 (20F66) image set"): 22 files, 8,979,698,218 bytes, `verify` ok, OS 165,519 / SystemOS
1,277 / AppOS 608 compressed files, all readable. Its `xnuhost.conf` (root tweaks, build 20F66): the 16.5 boot
arguments with `oneios-mac-exec-skip=mediaserverd,TVRemoteConnectionService` (kernel 0073: the other fork passed it on
its switch's command line; here the image carries it), the keybagd fixup (20F66's real `keybagd` matched its pinned
hash) and the QuartzCore vsync fixup. The root tweaks take a 20F66 root without `--any-version` since 2026-11-23.
What the tweaks report on that root (open): only 6 launchd jobs disabled (most of the 24A446 policy's labels are not
in 16.5), and no jetsam properties for V54 (the root has D22 and D221's): the guest's identity stays iPhone18,2 from
xnuhost's device tree, as in the other fork's run.

**The kernel.** `HOSTED_OUT=a56 ONEIOS_CRYPTO=original kernel/build-hosted.sh` (Linux PC, 2026-11-23, 311 s) gives
build id `xnu-12377.121.6-ios-27.0.1-24A446-c889b14b24f3`, the release kernel's (`kernel/release-kernel.txt`, v0.1.18
and v0.1.19), `"releasable": true`; the prelink (`KERNEL=... OUT=out/kernel/a56-24A446 kernel/prelink/build.sh`) passed
its audit (2,711 paired, 93 on the stub, 0 failures), `kernel.kc` `9e0da829...`. The A56 patches (0068, 0072-0074,
0077, 0004's and 0029's deltas) are in the main series, each inert or opt-in for iOS 27, and the S24 Ultra booted that
release kernel (v0.1.18, 13:45): **a released kernel already carries them, with the S24 Ultra unchanged.** A
`kernel.kc` is never released (Apple's kexts); the phone makes its own (Update the kernel, Make iOS image).

## In the OneOS fork (2026-11-23)

The fork's `oneios` branch (commit "iOS (OneiOS) on the Galaxy A56 (OneiOS issue 73)"; its docs/oneios.md "The
Galaxy A56 (iOS 16.5, untested)") applies docs/a56-oneos-fork.md section 1, in the form this tree allows:

- **The iOS kind on an SM-A566** (`OneiosSystem.PROFILE_IDS` has the A56; `TESTED_PROFILE_IDS` is the S24 Ultra only,
  so the A56 gets the not-this-phone warning with its own note and its tick before a switch). The S24 Ultra's gate,
  requests and switch command line are unchanged (its tests pin them).
- **Make iOS image** makes `OneiosImageChoice.of(phone)`: on the A56 the runtime's `lib/profiles/ios-16.5-a56.toml`
  (5,825,842,914 bytes to download, about 24 GiB room), after Apple's 24A446 kernelcache in `kb/` (Update the kernel's
  own fetch, decode, pin and `kbcache`, shared now), because the A56's `kernel.kc` is the 24A446 collection.
- **The switch** prints the A56's lines instead of the S24-only warning, and warns (never refuses) an A56 whose staged
  image is not 20F66. It passes **no A56 argument**: xnuhost's `galaxy-a56` row gives `gpu=2d` and the panel fallback,
  and the image's `xnuhost.conf` (root tweaks, build 20F66) gives the 16.5 boot arguments, the exec skip and the text
  fixups. Not taken from the other fork: `--display shm --gpu 2d --width/--height`, `--ram 4096M`, its `ram-*` sets,
  `ONEIOS_AMDGPU_RENDER_NODE` (no Xclipse host half here), renice and governor pinning, the 1800 s return timer.
- **RAM (2026-11-23).** `ram=auto` now counts 400 iOS tasks at 4 MiB, 7 % of the guest and a 1536 MiB headroom, all
  measured on the S24 Ultra with iOS 27 ([booter.md](booter.md) 2.2, "The terms of 2026-11-23"). On an 8 GB A56 that
  leaves the guest about 1.5 GiB for a MemAvailable of 5 GiB at the start [assumed: no A56 session log has it]. iOS
  16.5 with less RAM runs fewer tasks [guess]: once an A56 session logs its `tasks: 60 s: ... live N` and the
  pressure line, the image's `xnuhost.conf` can set `ram-tasks=` to what it measured.
- Open there: Update the kernel refuses a staged 20F66 image (`OneiosManifests.updateProblem` wants the kb's build,
  24A446), so a new kernel on an A56 means Make iOS image again; the app's texts still name iOS 27 in places (the
  system's name, the Make iOS image row's "about 11 GB").
- Tests: `./gradlew test` on the Linux build laptop, 726, 0 failures (core:model 379, core:root 341, core:safety 6;
  before: 717). The switch's shell tests ran under bash only (no dash or busybox there). Not run on any phone.

## The dual-version flow (how version selection works here)

The image set's build names the userland (`manifest.json` `build`, read by xnuhost into `image_set.build`):

- `24A446`: everything as before. The tree, the staged GPU code, roottweak's `xnuhost.conf` and the kernel's
  default paths are byte/behavior-identical to a tree without this port.
- `20F66`: xnuhost publishes the ramdisk as `RAMDisk1` too (loader `ramdisk1`, `runtime/loader`, docs/booter.md
  2.1); roottweak writes that image's `xnuhost.conf` with the 16.5 boot arguments (`oneios-gpu-metal=0`,
  `oneios-legacy-bootstrap-replies=1`, `oneios-legacy-registered-ports=1`, the keybagd + QuartzCore text fixups);
  the kernel's 16.5 shims engage (0068 and 0069/0072/0073 by boot argument, 0074 by layout). 0068 was "always
  compatibly" as ported, and was not: it broke every iOS 27 boot at launchd until 2026-11-21 (the next table). The OneOS fork's session script
  passes the rest (`--display shm --gpu 2d`, frame, `--set` flags): proposal, `docs/a56-oneos-fork.md`.

## Why 16.5 needed each piece (the fork's triage, condensed)

20F66's stock Metal opens `AGXAccelerator` as an IOGPU device client (type 1), which NativeAdreno refuses
(`0xe00002c7`): with the accelerator published, backboardd has a Metal device that cannot draw. `=0` leaves
CoreAnimation on the CPU — yet the panel stayed black, because 24A446's dispatch tables refused 20F66's swap
record (`0xe00002c2`: 0x46c vs 0x6e0) and surface info/limits sizes (0072 rewrites them field by field; the
header/plane maps are in the patch's comment). Then SpringBoard waited forever on
`com.apple.coremedia.systemcontroller.xpc`: mediaserverd died at exec with `OS_REASON_EXEC` 8 — Sandbox
refusing `mac_cred_label_update_execve` (0073 logs the policy, skips it for named executables). Touch is
still open in the fork: touches queue, vsync runs, but only 17 frames in the session and the first 2.25 s
after a touch-down; suspect IOHIDEventServiceUserClient 2/3 (`0xe00002c7`) or the shared-queue event format.

## Licence call (owner)

`ONEIOS_CRYPTO=original` removes the source-corecrypto reason a built kernel may not be released. **The owner's
call (2026-11-21): the hosted `ONEIOS_CRYPTO=original` kernel is the one a release carries** (kernel/README.md
"Releases and licences", docs/releases.md "The kernel in a release"). Its build record counts the source
corecrypto archive's symbols in the kernel (0 of 1191) and says `"releasable": true`; the default build stays
`source` (a local kernel, never released). A prelinked `kernel.kc` is never releasable (Apple's kexts).

## The Xclipse host half (not in this tree; audit of 2026-11-21)

The staged GPU3D amdgpu branch above is the guest side of a 3D path whose host side `main` does not have:
xnuhost here opens only KGSL (`gpu3d_kgsl.c` then, `runtime/xnuhost/src/gpu3d_kgsl.rs` since the Rust port), so on the A56 `gpu=auto` logs `gpu: 2D only: ...` and the guest gets
the 2D scanout (the fork's own 20F66 sessions pass `--gpu 2d` too). The fork's host half exists only as the binary
`tools/xnuhost_a56` (aarch64, NDK r27c, with debug info): its DWARF names `runtime/xnuhost/src/gpu3d_xclipse.c` (a
`--selftest-xclipse`: udmabuf import into the Xclipse GPU VA, a command buffer, a fence), a `gpu3d_kgsl.c` whose
open falls back to `amdgpu_renderer_probe` and whose context create calls `amdgpu_renderer_create` (virglrenderer's
`src/drm/amdgpu`, from a `virgl-android` tree), and libdrm 2.4.133's amdgpu library; it reads
`ONEIOS_AMDGPU_RENDER_NODE`. None of that source is in the fork's git (17 commits read), so nothing could be ported:
the ask to the fork is to publish `gpu3d_xclipse.c`, its `gpu3d_kgsl.c` changes and the libdrm/virglrenderer build.
Binaries never enter this tree. The read-only preflight `scripts/port/verify-host.sh` accepts the A56
(`SM-A566`/`a56x`/`s5e8855`) and prints its render node; `--set panel-fallback=1080x2340@120` gives xnuhost the A56's
panel where none is read (the fork pins `--width 1080 --height 2340` for 20F66 anyway).

## Touch on the A56 (open; audit of 2026-11-21)

Nothing in the fork's tree fixes it: the last fork commit (c6f0938) still says touches are queued to backboardd and
do not become gestures, with IOHIDEventServiceUserClient selectors 2 and 3 answering `0xe00002c7` as the first
suspect. That is an iOS 16.5 userland on 24A446's IOHIDFamily, not the A56's hardware: this tree's input path finds
`sec_touchscreen` by name and event4 is the A56's touch screen (the S24's side-key numbering does not apply). The fix
needs 20F66's and 24A446's IOHIDEventServiceUserClient dispatch tables side by side (Apple files: not here), then a
size-triggered rewrite in the pattern of `0072`. Not attempted without them.

## Not yet proven (needs an A56)

Done since the port (2026-11-23, Linux PC): the hosted kernel build with the five patches and the 0004/0029 deltas

   (the UDIF conversion, the 24A446 kernelcache fetched first, the prelink there), the switch and the return.
3. Touch: the other fork made touch work later with its own kernel patch 0079 (16.5's HID event layout, README.md

4. A56 specifics untouched: CPU clocks and governor, the S26-row pattern (hw-backend) if the A56 ever becomes a
   backend instead of a fork; the 16.5 root's jetsam target type (D22, not V54) and the launchd policy for 16.5 (6
   jobs disabled on that root, against 142 on 24A446).
